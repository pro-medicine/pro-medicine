### 결과 캐시 설계 판단

- 키에 넣는 값: 파이프라인·프롬프트 버전, 모델, 기준표·규칙 데이터 버전(행 해시), 응답자 유형, 성별, 나이, 생활습관 5개, 임신, 질환, 약 계열, 마스터에 없는 약 이름, 수면, 피로, 원하는 효과, **현재 섭취 성분 코드**(함량은 넣지 않음). 사용자 ID·응답 ID·시각·키·몸무게는 넣지 않는다
- 기준표나 규칙이 바뀌면 데이터 버전 해시가 바뀌어 캐시가 자동으로 무효화된다
- **민감 문항(질환·약·임신)이 포함된 입력도 캐시한다.** 키는 해시라 원문이 Redis에 남지 않고, 값은 성분 코드·이유·요약뿐이라 개인 식별 정보가 없다. 다만 이유 문장에 질환명이 들어갈 수 있어, 이유 문장까지 민감정보로 보는 정책이면 민감 입력은 캐시에서 빼야 한다 (팀 결정 필요)
- 저장소: `recommendation.cache.store=memory`(기본) | `redis`. Redis는 Docker `redis:7-alpine`으로 실제 연결 테스트를 통과했다 (`ResultCacheStoreTest`, `REDIS_HOST` 설정 시). Redis 오류는 캐시 미스로 처리
- Counter `recommendation.cache{result=hit|miss}`, Timer stage=`cache`

- LLM 호출이 2,000 → 809 (−59.6%), TPS 1.86배. 적중 요청은 수십 ms로 끝나 p50이 크게 내려갔다
- **V6의 p95·p99는 V4보다 높다.** 적중 요청이 빨리 끝나 같은 50명이 더 많은 요청을 보내면서, 캐시 미스 요청이 DB(H2)·서버 자원을 더 붐비는 상황에서 처리됐기 때문으로 보인다 (원인은 단계별 Timer로 더 봐야 한다)
- **캐시 스탬피드**: 서로 다른 조합은 710개인데 LLM 호출은 809번이다. 같은 입력이 동시에 들어오면 둘 다 미스로 LLM을 부른다 (99건). 같은 키의 첫 요청을 기다리게 하는 single-flight를 넣으면 줄일 수 있다 (다음에 할 것)
- 첫 시도(600건, 워밍업 없음, results.csv `08,V4-load-wiremock`, `08,V6-load-wiremock`)는 요청 600건에 서로 다른 조합이 368개라 적중 상한이 낮고 첫 웨이브 지연이 섞여 비교에 쓰지 않는다. 지우지 않고 남겼다

## 해석

- 결과 캐시는 반복되는 입력이 많을수록 효과가 크다. 실제 사용자 분포가 이 요청 세트(상위 20%가 57.6%)와 다르면 효과도 달라진다
- 최종 서비스 설정은 실제 API 측정 전이라 비용 수치로 고를 수 없다. 지금 근거로는 **V6(결과 캐시)**가 품질을 바꾸지 않고 LLM 호출을 줄이는 것이 확인됐고, V7·V8은 실제 토큰·품질 측정이 있어야 판단할 수 있다 → progress "결정한 것"에 기록
