# AI 추천 실제 성능 측정 리포트 (OpenAI 284회 + WireMock 부하·장애)

- 측정일: 실제 OpenAI 2026-10-22, WireMock 부하·장애 2026-10-26
- 출처: `docs/perf/results.csv`의 2026-10-22 행(실제), 2026-10-26 행(WireMock). 호출 단위 원자료는 `docs/perf/runs/*-openai-*.json`의 `llmCallLogs`
- **평가셋은 검토 전(`reviewed=false`) 상태로 측정했다.** 기대값(추천해야 할 성분·금지 성분·용량)을 사람이 확정하지 않았으므로 recall·precision은 상대 비교용이다.

## 1. 한 줄 요약

- 서버 용량 계산(V2)으로 **용량 오류율 0.75~1.0 → 0**, LLM p95 **34.9초 → 17.6초**. 출력 토큰도 498 → 366으로 줄었다. (`04,V0` / `05,V1` / `06,V2`)
- 추론 강도 `low`로 V4의 LLM p95 **17.2초 → 13.4초**, 요청당 비용 $0.0051 → $0.0046, recall 동일(0.923). (`07,V4` / `07,V4-low`)
- 모델 라우팅(V8)으로 요청당 비용 **$0.0051 → $0.0031** (-39%), recall 동일. 결과 캐시(V6) 2회차는 OpenAI 호출 0, e2e p95 0.84ms. (`08,V8` / `08,V6-pass2`)
- **발견한 문제:** `llm.timeout-ms`(30초)가 OpenAI 전환(e11fb07) 이후 HTTP 클라이언트에 연결되지 않아 실제로는 약 60초에서 끊긴다. 실제 타임아웃 3건이 모두 60.0초였고, WireMock slow(20초) 시나리오에서도 V10의 15초 타임아웃이 한 번도 걸리지 않았다. (5장, 7-3)
- 부하(WireMock): 결과 캐시로 LLM 호출 2,000 → 809, TPS 15.8 → 37.2. V10은 flaky 0.905 → 1.0, 전면 장애 0.5 → 1.0 (폴백 포함). (7장)

### 5-1. 실측 분포 (성공 호출 기준)

V2 이후 성공 호출 중 N초를 넘긴 비율:

| 기준 | 10초 | 12초 | 15초 | 18초 | 20초 | 25초 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 비율 | 45.7% | 24.2% | **5.5%** | 1.8% | 0.5% | 0% |

- V0·V1은 출력이 길어 느리다 (p95 54.3초, 34.9초).
- 타임아웃 3건(V0 1, V1 1, V4-repro 1)은 모두 **60.0초**에 끊겼다 (`latencyMs` 60012~60022, `outcome=TIMEOUT`).

### 5-2. 발견: `llm.timeout-ms`가 적용되지 않음

- 설정값은 30초(`LlmProperties.timeoutMs` 기본 30000)인데 실제 끊긴 시간은 60초다.
- 원인: OpenAI 전환 커밋(e11fb07)에서 기존 HTTP 클라이언트의 `setReadTimeout(timeoutMs)`가 빠졌고, 지금 `timeoutMs`를 읽는 운영 코드가 없다 (`grep getTimeoutMs src/main` 결과 없음). 그래서 Spring AI 기본 HTTP 클라이언트의 시간 제한(약 60초)으로 동작한다.
- 영향: 응답이 없는 호출이 60초 동안 워커 1개를 잡는다. V10 재시도를 켜면 최악 60초 × 시도 수까지 늘어난다.
- 이번 작업에서는 운영 코드를 고치지 않았다 (계획 범위 밖). 고칠 때는 Spring AI OpenAI 모델이 쓰는 RestClient에 읽기 시간 제한을 넣는다.

### 5-3. 타임아웃 권고

- **15초(V10 권장값)는 짧다.** 정상 응답의 5.5%가 잘린다. 재시도로 이어지면 비용과 지연이 더 늘어난다.
- **25~30초를 권한다.** V2 이후 정상 응답의 최대가 22.8초였고 25초를 넘긴 정상 응답은 없었다. 30초면 기존 설정값 그대로다.
- 전제: 위 5-2의 연결 문제를 먼저 고쳐야 어떤 값이든 적용된다.

## 7. 부하·장애 (WireMock, 실제 호출 0회)

- 조건: 테스트 JVM 안에서 부하 생성 (k6 대체), H2, WireMock이 OpenAI 형식 응답을 **3초 고정 지연**으로 반환 (slow 시나리오는 20초). 실제 OpenAI는 부르지 않는다 (`perfTest`에는 API 키를 넘기지 않음).
- 비교 대상: 2026-10-21 행은 OpenAI 전환 전(Claude 형식), 2026-10-26 행은 OpenAI 형식 + Spring Boot 4. 같은 PC지만 측정마다 ±40% 정도 흔들린다.
- 출처: `results.csv` step 08~10, date 2026-10-26 (상세는 note의 `detail=` JSON)

### 7-1. 결과 캐시 (STEP 08, 요청 2,000건, 사용자 50명)

| label | WireMock 호출 | TPS | p95 | p50 |
| --- | ---: | ---: | ---: | ---: |
| V4-load-wiremock-2000 | 2,000 | 15.8 | 3,086ms | 3,021ms |
| V6-load-wiremock-2000 | **809** | **37.2** | 3,046ms | **9ms** |

- 같은 조건 요청이 섞이면 LLM 호출이 60% 줄고 TPS가 2.4배가 된다. 10-21(28.2 TPS, 호출 809)과 같은 경향이다.
- p95는 그대로다. 캐시에 없는 요청은 여전히 LLM을 기다리기 때문이다.

### 7-2. 처리 구조 (STEP 09, 10초에 600건 몰림)

| label | TPS | p95 | 에러율 | LLM 동시 호출 최대 | 메모 |
| --- | ---: | ---: | ---: | ---: | --- |
| V9-sync-spike-burst | 16.2 | 26,932ms | 0 | 50 | Tomcat 스레드 50개가 모두 LLM 대기 |
| V9-vt-spike-burst | 46.2 | 3,023ms | 0 | **185** | 가상 스레드, 동시 호출 상한 없음 |
| V9-queue-spike-burst | 6.5 | 78,906ms (완료) | 0 | 20 | 접수 p95 695ms, 워커 20개가 차례로 처리 |

- 가상 스레드가 가장 빠르지만 LLM 동시 호출이 185까지 올라간다. 실제 OpenAI에서는 rate limit(분당 요청·토큰)에 그대로 걸리는 구조다.
- 큐는 접수만 바로 하고(695ms) 완료는 늦지만, OpenAI 동시 호출을 워커 수(20)로 묶는다.
- 10-21보다 sync 에러율이 0.04~0.23 → 0, vt p95가 21~29초 → 3초로 달라졌다. Spring Boot 4 업그레이드 영향으로 보이지만 원인은 확인하지 않았다.
- **실제 지연으로 환산:** 실제 LLM은 3초가 아니라 p50 약 10초다. 워커 4개(기본값)면 분당 약 24건, 20개면 약 120건을 처리한다. 출력 한도 2,000일 때 OpenAI TPM 기준 상한은 분당 약 330건이다 ([llm-safeguards.md](../llm-safeguards.md) 5장).

## 9. 한계와 다음 단계

- 평가셋이 검토 전(`reviewed=false`)이다. recall 대상 13, 용량 대상 8케이스로 작아서 1건 차이가 0.04~0.13씩 움직인다.
- 실행별 1회 측정이다. 같은 시간대에 순서대로 돌려 네트워크·OpenAI 부하 차이가 섞여 있다 (V0·V1이 먼저 실행됨).
- 실제 API로 동시 호출·부하는 하지 않았다 (rate limit, 비용). 부하는 WireMock 3초 고정 응답 기준이다.
