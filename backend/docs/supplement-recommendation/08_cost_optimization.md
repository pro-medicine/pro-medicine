# STEP 08. 비용 최적화 - 결과 캐시 · 프롬프트 캐싱 · 모델 라우팅

> 먼저 `docs/prompts/00_COMMON.md`, `docs/prompts/reference/measurement.md`를 읽고 따른다. STEP 07이 끝난 상태에서 시작한다.

## 목표

품질(V4 수준)을 유지하면서 요청당 비용과 지연을 줄인다. 세 가지를 하나씩 붙이고 각각 측정한다.
이 STEP부터는 품질 지표가 **떨어지지 않았는지**도 같이 확인한다.

| 버전 | 바뀌는 점 |
| --- | --- |
| V6 | 정규화 입력이 같으면 LLM을 다시 부르지 않고 이전 결과 재사용 (Redis) |
| V7 | 매번 같은 시스템 프롬프트·규칙 설명·tool 정의에 Claude 프롬프트 캐싱 적용 |
| V8 | 입력 복잡도에 따라 작은 모델 / 기본 모델 선택 |

구성은 효과를 따로 재기 위해 이렇게 고정한다.
- V6 = V4 + 결과 캐시
- V7 = V4 + 프롬프트 캐싱 (결과 캐시는 끈다. 둘을 같이 켜면 프롬프트 캐싱 효과를 따로 볼 수 없다)
- V8 = V7 + 모델 라우팅
- 최종 서비스 설정은 STEP 08 리포트의 결과를 보고 고르고, 고른 조합과 이유를 progress에 적는다

## 1. V6 결과 캐시

- Redis 추가 (`docker-compose.yml`에 redis 서비스, 테스트는 Testcontainers 또는 embedded 대안).
- 캐시 키: 정규화 입력에서 **추천에 영향을 주는 값만** 골라 정렬한 뒤 SHA-256. 사용자 ID, 응답 ID, 시각은 넣지 않는다. 키에 들어가는 필드 목록을 클래스 상수로 명시한다.
- 키에 `pipeline_version`, `prompt_version`, 기준표·규칙 데이터 버전을 포함한다. 규칙이 바뀌면 캐시가 자동으로 무효화되게 한다.
- 값: LLM 출력(성분·이유)만 캐시한다. 용량 계산과 규칙 검증은 캐시 적중이어도 매번 다시 한다 (현재 섭취량이 다를 수 있음).
- TTL 기본 7일, 설정값으로.
- 민감 문항이 포함된 입력도 캐시한다. 단 키는 해시라 원문이 Redis에 남지 않고, 값에는 개인 식별 정보가 없다. 이 판단을 리포트에 적는다.
- Counter: `recommendation.cache` (태그 result=hit|miss)

## 2. V7 프롬프트 캐싱

- 변하지 않는 부분(시스템 프롬프트, 규칙 설명, tool 정의)을 앞에 두고 캐시 지점을 표시한다. 요청 형식과 최소 캐시 길이 조건은 공식 문서에서 확인한다.
- 고정 부분이 최소 캐시 길이보다 짧으면 **프롬프트를 일부러 늘리지 않는다.** 캐시가 적용되지 않는다는 사실과 길이를 그대로 기록한다.
- 사용자마다 바뀌는 부분(입력, 금지 성분 목록)은 캐시 지점 뒤에 둔다. 금지 목록이 앞에 있으면 캐시가 안 먹으니 순서를 확인한다.
- `llm_call_logs.cache_read_tokens`, `cache_creation_tokens`로 효과를 본다.

## 3. V8 모델 라우팅

- `ModelRouter`: 정규화 입력의 복잡도로 모델을 고른다. 기준은 단순하게 시작한다.
  - 복잡: 복용 약 1개 이상, 또는 질환 1개 이상, 또는 적용 규칙 3개 이상 → 기본 모델
  - 그 외 → 작은 모델
- 작은 모델 이름은 공식 문서에서 확인해 설정값으로 둔다.
- 라우팅 결과를 `llm_call_logs.model`로 확인할 수 있다.

## 4. 측정

### 품질·비용 (평가셋)

1. `evalRun -PpipelineVersion=V6`: 같은 평가셋을 **두 번 연속** 실행한다. 1회차는 캐시 미스, 2회차는 적중 상황이다. 두 줄 모두 기록한다.
2. `evalRun -PpipelineVersion=V7`
3. `evalRun -PpipelineVersion=V8`, 그리고 평가셋의 `difficulty`별로 recall을 나눠서 본다

### 부하 상황의 캐시 효과 (k6)

- 실제 사용 패턴을 흉내 낸 요청 세트: 프로필 조합 1,000건 중 일부가 반복되도록 만든다 (예: 상위 20% 조합이 요청의 60%). 생성 스크립트와 분포를 리포트에 적는다.
- LLM은 WireMock으로 대체하고 고정 지연(예: 3초)을 준다. 실제 API로 부하 테스트하지 않는다.
- k6로 같은 요청 세트를 V4, V6에 각각 보내고 TPS, p95, LLM 호출 수를 비교한다.
- k6 스크립트는 `perf/k6/`에 두고, 실행 명령을 리포트에 적는다.
