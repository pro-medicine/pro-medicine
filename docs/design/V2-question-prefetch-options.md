# V2 맞춤 질문 대기 방식 두 가지 (사용자 조사 후 결정)

- 작성: 2026-10-28, 영준 + Claude
- 상태: **결정 전**. 사용자 조사 결과를 보고 기본값을 정한다. 지금 기본값은 A안이다.
- 관련 설정: `pq.prefetch-strategy` (`backend/docs/api/personalized-api.md` 7장)

## 1. 두 가지 버전

| | A안: 질문마다 그때 생성 (기본) | B안: 미리 만들어 바로 보여 주기 |
|---|---|---|
| 설정 | `pq.prefetch-strategy=NONE` | `pq.prefetch-strategy=UPFRONT_FOLLOWUP` |
| 동작 | 답할 때마다 다음 질문을 GPT에 1개씩 요청 | 시작할 때 질문 묶음을 만들고, 이어질 2단계 질문도 미리 만든다. 답하면 만들어 둔 질문을 바로 보여 준다 |
| 사용자 체감 | 첫 질문이 빨리 나온다. 답할 때마다 몇 초씩 기다린다 | 첫 질문까지 오래 기다린다. 그 뒤로는 거의 기다리지 않는다 |

## 2. 측정 결과 (2026-10-27, 실제 GPT 측정)

조건
- 모델: gpt-6.1-sol
- 회차: 방식마다 10회차(페르소나 5명 + 같은 사람 5회)
- 가상 사용자: 질문을 받고 **3초 생각한 뒤 답함**. 아래 시간은 이 3초를 뺀, 사용자가 실제로 기다린 시간이다.

| 지표 | A안 | B안 |
|---|---|---|
| 첫 질문까지 대기 p50 / p95 | **6.3초** / 10.0초 | 12.2초 / 19.5초 |
| 답한 뒤 다음 질문 대기 p50 / p95 | 4.4초 / 6.9초 | **0.0초** / 12.4초 |
| 회차 전체 대기 평균 / p95 | **23.0초** / **29.0초** | 23.2초 / 31.8초 |
| 회차당 LLM 호출 | 5.5회 | 4.0회 |
| 회차당 비용 | **$0.0204** | $0.0268 (+31%) |
| 품질(안전 위반·질문 반복·계획 준수) | 위반 0, 반복 0, 준수 1.0 | 같음 |

- 출처: 로컬 측정 파일
  - A안: `openai-20261027-103929`, `openai-20261027-135316`
  - B안: `openai-20261027-143057`, `openai-20261027-143547`
  - 위 파일과 상세 리포트(`backend/docs/perf/V2-latency-report.md`)는 로컬 전용이다.
- 회차 전체 대기 합계는 거의 같다. **차이는 기다리는 시점**이다. A안은 질문마다 조금씩 나눠 기다리고, B안은 처음에 몰아서 기다린다.
- B안이 비용이 더 드는 이유
  - 묶음 호출은 질문 여러 개를 한 번에 쓰므로 출력이 길다.
  - 답에 따라 쓰지 않고 버리는 질문이 40~50% 생긴다.
- B안에서도 답→다음 질문이 늦어지는 경우가 있다(p95 12.4초). 미리 만든 질문이 답과 맞지 않으면 그때 1개를 새로 만들기 때문이다.

## 3. 버전 바꾸는 법

| 방법 | A안 | B안 |
|---|---|---|
| 프로필 | 추가 없음 | `--spring.profiles.active=local-llm,pq-upfront` (`application-pq-upfront.yml`) |
| 실행 인자 | `--pq.prefetch-strategy=NONE` | `--pq.prefetch-strategy=UPFRONT_FOLLOWUP` |
| 환경변수 | `PQ_PREFETCHSTRATEGY=NONE` | `PQ_PREFETCHSTRATEGY=UPFRONT_FOLLOWUP` |

- 서버를 다시 시작해야 바뀐다. 프론트엔드와 API는 두 버전에서 같다.
- 이중 요청(`pq.hedge-enabled`)은 두 버전 모두 끈 상태를 권장한다.
  - 측정에서 10회차 중 1번 실행됐고, 원래 요청이 먼저 와서 효과가 없었다.

## 4. 사용자 조사 방법 (제안)

- 같은 사람이 두 버전을 모두 해 본다. 순서 효과를 줄이려고 절반은 A → B, 절반은 B → A 순서로 한다.
  - 버전마다 서버를 다시 띄우거나, 서버 두 대를 띄운다(포트를 다르게).
- 회원 계정으로 V2 맞춤 질문을 끝까지 진행한다. 예시 데이터 계정을 쓰고 실제 개인정보는 넣지 않는다.
- 끝난 뒤 묻는 질문
  1. 어느 쪽이 더 빠르게 느껴졌나요? (A / B / 비슷함)
  2. 기다리는 동안 답답했던 순간이 있었나요? (처음 / 중간중간 / 없음)
  3. 다시 쓴다면 어느 쪽을 고르겠어요? 이유는?
  4. 첫 화면에서 기다릴 때 그만두고 싶었나요? (B안만)
- 같이 기록할 것: 회차마다 첫 질문 대기와 답→다음 질문 대기(서버 `pq.*` 지표), 중간에 닫은 회차 수
- 판단 기준(제안): 3번에서 과반이 고른 쪽. 비슷하면 비용이 낮은 A안

## 5. B안을 고를 때 같이 할 일 (협의 필요)

- **첫 질문 로딩 문구 (2026-10-28 반영)**: 첫 질문 대기와 다음 질문 대기에 문구를 따로 쓴다(`frontend/src/recommendation/PersonalizedModal.jsx`).
  - 첫 질문: "건강정보를 살펴보고 있어요 → 나에게 맞는 질문을 고르고 있어요 → 질문을 준비하고 있어요"(3초 간격). 안내 "10초 정도 걸릴 수 있어요"를 함께 보여 준다.
  - 다음 질문: 기존 문구 그대로 쓴다("답변을 살펴보고 있어요 → … → 거의 다 만들었어요", 1.7초 간격).
  - 바뀌기 전에는 첫 질문에도 다음 질문 문구를 썼다. 그래서 답이 없는데도 "답변을 살펴보고 있어요"가 나왔고, B안에서는 "거의 다 만들었어요"가 10초 넘게 떠 있었다.
  - 두 버전에 같은 문구를 쓴다. A안에서도 첫 질문 p95가 10초다.
- **운영 비용**: 회차당 약 $0.0064 더 든다(측정 기준).
- **서버 메모리**: 미리 만든 질문은 서버 메모리에 보관한다. 서버를 다시 시작하면 사라지고, 그때는 A안처럼 1개씩 만든다.

## 6. 한계

- 생각 시간을 3초로 고정했다. 실제 사용자가 더 오래 생각하면 결과가 달라질 수 있다.
- 가상 사용자가 규칙대로 답했다. 실제 답 분포와 다르다.
- 방식마다 10회차뿐이라 p95는 값 몇 개에 흔들린다.
- 사람이 느끼는 체감은 측정하지 않았다. 그래서 이 사용자 조사가 필요하다.
