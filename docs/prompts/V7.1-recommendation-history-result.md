## 3. API 명세

모두 회원 전용입니다. 토큰이 없으면 401 `E003`, 남의 기록이거나 없는 기록이거나 끝나지 않은 추천이면 404 `R001`을 돌려줍니다(존재 여부를 숨김). LLM·임베딩은 호출하지 않습니다.

**목록** `GET /api/v1/users/me/recommendations/history`

```json
{ "items": [
  { "source": "V4_CHAT", "recommendedAt": "2026-11-03T17:01:05", "recommendationId": null, "chatResultId": 88,
    "concern": { "type": "TEXT", "labels": [], "text": "피곤해요", "answer": "오후에요" },
    "ingredients": ["MAGNESIUM"] },
  { "source": "V2_PERSONALIZED", "recommendedAt": "2026-07-01T21:03:11", "recommendationId": 345, "chatResultId": null,
    "concern": { "type": "EXPIRED", "labels": [], "text": null, "answer": null },
    "ingredients": ["MAGNESIUM", "VITAMIN_B12"] }
]}
```

- 대상
  - ① `ai_recommendations` 중 `status = DONE`이고 `user_id`가 나인 것 (V1·V2·V4 트랙 2). 기준 시각은 `finished_at`.
  - ② `ai_chat_results` 중 `track = REVIEW`이고 `user_id`가 나인 것. 기준 시각은 `created_at`.
  - 완료 시각 최신순으로 최대 20건(`RecommendationHistoryService.LIMIT`)을 보여준다. 시각이 같으면 ① 먼저, 그다음 id 큰 순이다.
- `concern.type`
  - `LABELS`: V1 Q-GOAL 또는 V2 CONCERN_OPEN에서 고른 선택지 라벨.
  - `TEXT`: V4 문장. `answer`는 되묻기에 답했을 때만 있다.
  - `NONE`: `text`가 "특별히 불편한 점 없음" / "잘 모르겠음"이다. 답이 없으면 `text`는 null.
  - `EXPIRED`: 90일이 지나 원본이 지워졌다.
- **초안과 다른 점**: `concern.answer` 필드를 추가했다(V4 되묻기 답). `ingredients`에는 제외 성분이 들어가지 않는다.
- 90일 뒤 회차·대화 세션이 지워진 추천은 대화 결과 행(RULE_BASED)이 남아 있는지로 V2와 V4 트랙 2를 구분한다.

**상세** `GET .../history/{recommendationId}` (V1·V2·V4 트랙 2), `GET .../history/chat/{chatResultId}` (V4 트랙 1)

```json
{ "source": "V2_PERSONALIZED", "recommendationId": 345, "snapshot": true, "notice": "입력하신 약·질환 기준으로 …",
  "ingredients": [ { "ingredient": "MAGNESIUM", "reason": "…", "sortOrder": 1, "warnings": [],
    "products": [ { "catalogProductId": 9305, "productName": "…", "brand": "Solgar", "imageUrl": null, "price": null,
                    "alsoContains": [], "cautions": [], "warnings": ["저장된 경고"] } ] } ] }
```

- ① 저장된 순위가 있으면 그대로 보여준다(`snapshot: true`).
  - 이름·사진·참고 가격·공통 주의점은 지금 값, 같이 든 성분·안전 경고는 추천받을 때의 값이다(P1).
  - 저장된 순위가 없으면(V7.1 이전 추천) V7처럼 `recommend()`로 다시 계산한다(`snapshot: false`). 90일 지난 예전 V2·V4 추천은 조건을 다시 만들 수 없어 제품이 빈 목록이 된다.
- ② 저장된 `cards`를 그대로 보여준다(`snapshot: true`).
- 둘 다 지금 판매 중단(`is_active = 0`)·차단(`blocked_kr`)된 제품은 뺀다(D12).
- 소유권은 `user_id`로 확인한다. `RecommendationAccess.requireOwned`는 90일 뒤 FK가 비면 거부하므로, 기록 화면에서는 일부러 `user_id` 기준을 쓴다. 90일 이내에는 두 결과가 같다.

## 4. 제품 순위 저장 흐름과 DONE 경로별 확인 (승인 시 요청 1)

| 경로 | DONE 저장 메서드 (`RecommendationStore`) | 트랜잭션 안에서 이벤트 발행? | 테스트 (실제 커밋) |
|---|---|---|---|
| V1 회원 (동기) | `save` (`@Transactional`) | ✅ | `V1_회원_설문_추천은_DONE_뒤…` 통과 |
| V1 RULE_ONLY 폴백 | `save` (LLM 장애 → 규칙 결과) | ✅ | `V1_RULE_ONLY_폴백도…` 통과 |
| V1 비회원 | `save` | 발행 안 함 (`user_id` 없음) | `비회원_V1_추천은…저장하지_않는다` 통과 |
| V2 | `saveForSession` (바깥 `PersonalizedSessionStore.complete` 트랜잭션에 참여) | ✅ (바깥 트랜잭션 커밋 뒤 실행) | `V2_정밀_추천은_바깥_트랜잭션_커밋_뒤에…` 통과 |
| V4 트랙 2 (요청 스레드, `async=false`) | `complete` (`@Transactional`) | ✅ | `V4_트랙2_요청_스레드…` 통과 |
| V4 트랙 2 (백그라운드 `chat-fallback` 스레드) | `complete` | ✅ (그 스레드의 트랜잭션) | `V4_트랙2_백그라운드_실행기에서도…` 통과 |

- V1 큐 경로는 지금 코드에 없다(`RecommendationService.create`는 동기만).
- 세 메서드가 모두 `@Transactional`이라 지금은 트랜잭션 없이 이벤트가 발행되는 경우가 없다. 그래도 나중을 대비해 `@TransactionalEventListener(AFTER_COMMIT, fallbackExecution = true)`로 두었다.
- 리스너는 커밋 뒤 같은 스레드에서 실행된다.
  - 성분마다 `TransactionTemplate(REQUIRES_NEW)` 안에서 `recommend()`를 부르고 결과를 INSERT한다. 조건 로더와 `ProductSafetyFilter`를 그대로 거친다.
  - AFTER_COMMIT 안의 데이터 접근은 끝난 트랜잭션에 참여하기 때문에 새 트랜잭션을 연다.
- 실패 처리
  - 성분 하나가 실패하면 그 성분만 롤백한다. `log.warn`(추천 id·성분 코드·예외 이름만)과 메트릭 `recommendation.products.snapshot{outcome=success|fail}`을 남기고, 추천은 DONE 그대로다.
  - 리스너는 예외를 밖으로 던지지 않는다.
  - 이미 저장된 추천과 비회원 추천은 건너뛴다. 제품 0개인 성분은 행이 없다.
- 이 테스트 클래스는 커밋해야 리스너가 돌기 때문에 `@Transactional`을 걸지 않았다. 리뷰 제품 시드와 만든 행을 테스트마다 직접 지운다(같은 H2 DB를 다른 테스트와 공유).
- 기존 테스트에 미치는 영향
  - 기존 API 테스트는 `@Transactional`(롤백)이라 AFTER_COMMIT 리스너가 돌지 않아 결과가 그대로다.
  - 트랜잭션 없이 도는 기존 테스트(`FallbackTest` 등)에서는 저장이 실행되지만, 그 테스트에는 리뷰 제품 데이터가 없어 행이 생기지 않고 결과도 같다.

## 5. `ai_chat_results` 세션 NULL 허용으로 바뀐 코드와 90일 정리 후 동작

- `AiChatResult`: `chatSession`은 optional + `@OnDelete(SET_NULL)`, `user` 추가, `chatSessionIdOrNull()` 추가.
- `ChatSessionStore.saveReviewResult`(일반 저장과 V5 재사용 복사)와 `startFallback`이 결과 행에 `user`를 넣는다.
- 세션 id로 찾는 곳은 바꾸지 않았다: `result`, `findReusable`, `ChatRecommendationService.get`·`snapshot`, `ChatFallbackRunner.cleanUpInterrupted`. 세션이 없는 결과 행은 대화 API·V5 재사용 대상에 잡히지 않는다(테스트로 확인).
- V7 `RecentRecommendationService`: `chat.getChatSession().getChatSessionId()`를 `chatSessionIdOrNull()`로 바꿔 NPE를 막았다.
  - `/recent` 쿼리는 그대로(세션 inner join)라 90일 지난 트랙 1 결과는 지금처럼 `/recent`에 나오지 않는다(D13: 동작 그대로).
- 90일 정리
  - `deleteStartedBefore`는 JPQL 벌크 삭제라 DB FK가 그대로 동작한다.
  - `ai_chat_turns`(원문)와 `ai_question_turns`는 삭제되고, 트랙 1·트랙 2 결과는 남고 세션 id만 NULL이 된다(H2 테스트, MySQL 임시 DB 모두 확인).

- 정리 스케줄러에 로그 `survey goal answers purged: count=…`와 메트릭 `survey.goal.purged`를 추가했다.
- 원문은 로그에 남기지 않는다. 새 로그는 id·성분 코드·건수·예외 이름만 남긴다.

## 12. 후속 항목

1. **회원 탈퇴 시 추천 결과 처리 결정 필요(D15)**: 지금은 `ai_recommendations.user_id`·`ai_chat_results.user_id`가 `ON DELETE SET NULL`이라 탈퇴해도 추천 결과(성분·제품 순위)가 익명으로 남는다. 탈퇴 기능을 만들 때 CASCADE로 바꿀지 정해야 한다.
2. **P1 `warnings`·`ai_recommendation_items.warnings`는 90일 삭제 대상이 아니라 계속 보관된다.** 사용자의 약·질환에서 나온 경고 문구가 들어 있을 수 있으니 건강정보 보관 동의 작업 때 대상 여부를 정해야 한다.

4. V5 재사용으로 같은 내용의 기록이 2건 생길 수 있다(중복 제거 안 함).
5. 건강정보 보관 동의(1년/90일)가 정해지면 `RETENTION_DAYS`·Q-GOAL 삭제와 연결한다.
