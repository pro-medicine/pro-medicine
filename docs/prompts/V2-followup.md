## 1. "그만하기" → 버튼 2개
1. **✕ 닫기**: 질문만 닫고 추천은 하지 않음. 회차 상태 `ABANDONED`(사용자 중단), `stopped_by_user = true`.
   서버 API는 `POST /api/v1/personalized-sessions/{id}/close`로 추가하거나 기존 stop을 바꿔도 됨 (API 문서 같이 수정).
2. **"여기까지 답하고 결과 보기"**: 지금까지 답으로 정밀 추천 (기존 stop 동작).
   단, 임신 고정 질문 대상자는 그 질문에 답하고, LLM 질문도 1개 이상 답한 뒤에만 활성화. 서버도 같은 조건을 검증해서 아니면 `PQ003`.
- 테스트: 닫기, 조건 미충족 시 결과 보기 거절
- 설계 문서 D8, API 문서 수정

## 2. 타임아웃 설정 실제 적용 (전제)
- `live-performance-report.md`에서 발견: `llm.timeout-ms`(30초)가 OpenAI HTTP 클라이언트에 연결되지 않아 실제로는 약 60초에서 끊김. 아직 수정 커밋 없음
- `spring.ai.openai.chat.timeout`이 실제 읽기 타임아웃에 적용되는지 확인하고, 안 되면 Spring AI가 쓰는 HTTP 클라이언트(RestClient 등)의 read timeout을 `llm.timeout-ms`로 설정
- 테스트: WireMock 등으로 지연 응답을 주고 설정한 시간에 `LlmCallException(TIMEOUT)`이 나는지 (기존 테스트 구조 재사용)
- V1 동작(재시도·서킷·폴백)이 그대로인지 기존 테스트로 확인

## 3. 질문 미리 만들기 — 방식 4가지를 모두 구현해 측정하고 최적안 선택
**배경 (어제 실제 측정 10회차 기준)**: 회차당 호출 = 질문 수 + 정밀 추천 1회. 실험 A 평균 4.8회, 실험 B 6회, 최악 8회. 프로필로 정해지는 주제(`MED:*`, `CONDITION:*`, `LIFESTYLE:*`)의 1단계 질문 25개 중 실제로 물은 것은 13개(52%). 약물 첫 질문은 약이 있는 사용자 전원에게 쓰였다.

**설정 하나로 방식을 바꿀 수 있게 구현한다**: `pq.prefetch-strategy`

| 값 | 방식 | 내용 |
|---|---|---|
| `NONE` | 기존 | 질문마다 1회씩 그때 생성 (지금 동작, 기준선) |
| `BACKGROUND` | 방식 ① 대기 시간 우선 | 첫 질문(임신 고정 질문 또는 불편한 점)은 지금처럼 **바로** 생성해서 응답. 그와 **동시에 백그라운드에서** 프로필 주제 1단계 질문들을 **1회 묶음 호출**로 생성. 서버가 그 주제를 고르면 LLM 호출 없이 사용 |
| `UPFRONT` | 방식 ② 호출 수 우선 | 회차 시작 시 **불편한 점 질문 + 프로필 주제 1단계 질문을 한 번의 호출로 같이** 생성한 뒤 첫 질문을 응답 (첫 응답이 묶음만큼 늦어짐, 별도 호출 1회가 줄어듦) |
| `UPFRONT_FOLLOWUP` | 방식 ③ 최대 감소 | ②에 더해 (a) 불편한 점에 답하면 파생 주제(최대 2개)의 1단계 질문을 1회로 묶어 생성, (b) 각 1단계 질문을 만들 때 "CONCERN을 고르면 이어질 2단계 질문"도 함께 생성해 두고 CONCERN이면 사용 (2단계 질문은 실제로 고른 선택지를 모르고 만들어짐 → 품질 영향을 반드시 측정) |

공통 규칙
- 묶음 출력 스키마는 질문 배열. 질문마다 기존 검증기를 그대로 적용하고 통과한 것만 보관. 실패한 주제는 그때 단건 생성
- 묶음에 넣을 프로필 주제 수: 주제 계획 순서대로 최대 4개(= 새 주제 예산 5 − 불편한 점 1). 계획 단계에서 기준 제안
- 미리 만든 질문은 이전 답을 모르고 만들어졌으므로, 사용 직전에 이 회차의 이전 질문과 반복 검사를 다시 적용. 걸리면 단건 생성
- 미리 만든 질문이 아직 생성 중이면: 기다릴지 단건 생성할지 계획 단계에서 제안 (방식 ①)
- 보관 위치: 회차 단위(DB 또는 메모리 캐시) — 서버 재시작 시 잃어도 단건 생성으로 대체되면 됨
- `llm_call_logs.call_tag`: `PQ_QUESTION_BATCH`, `PQ_QUESTION_FOLLOWUP_BATCH` 추가
- 메트릭: 미리 만든 질문 수, 사용(적중) 수, 버린(낭비) 수
- 기본값은 측정 후 선택한 방식으로 설정 (측정 전까지는 `NONE`)

## 4. 느린 호출 대비 이중 요청 (질문 생성만)
- 질문 생성 호출이 **N초**(기본 8초, 설정값 `pq.hedge-after-ms`) 안에 응답이 없으면 같은 요청을 하나 더 보내고, **먼저 성공한 응답**을 쓴다. 늦은 쪽은 취소(가능하면)하거나 결과를 버린다
- 이중 요청은 질문 1개당 최대 1번. 정밀 추천에는 적용하지 않음
- 두 호출 모두 `llm_call_logs`에 남긴다 (`call_tag`: `PQ_QUESTION_HEDGE` 추가, 버린 호출도 비용은 기록)
- 재요청(검증 실패 시 1회)·재시도·서킷과 겹칠 때의 순서를 계획 단계에서 정리할 것 (예: 이중 요청은 첫 시도에만)
- 메트릭: 이중 요청 발생 횟수, 두 번째가 이긴 횟수, 추가 비용
- 테스트: 첫 응답이 늦으면 두 번째 응답 사용, 둘 다 늦으면 타임아웃, 첫 응답이 빨리 오면 이중 요청 안 함

## 5. 방식별 비용·시간 측정 → 최적안 선택
**같은 조건**(같은 페르소나·답 정책·모델·설정)으로 아래를 실제 API로 실행한다. 실험 A(사용자 5명 × 1회) + 실험 B(A1 × 5회) = 방식당 10회차.

| 실행 | prefetch-strategy | 이중 요청(4번) |
|---|---|---|
| R0 기준선 | `NONE` | 끔 — **어제 결과**(A `openai-20261026-201214`, B `openai-20261026-201739`)를 쓰되, 2번 타임아웃 수정 후 다시 돌려 기준선을 새로 잡는 것을 권장 (계획 단계에서 결정) |
| R1 | `BACKGROUND` | 끔 |
| R2 | `UPFRONT` | 끔 |
| R3 | `UPFRONT_FOLLOWUP` | 끔 |
| R4 | R1~R3 중 최적안 | **켬** (이중 요청 효과만 따로 보기) |

- 비용 상한: 전체 합계 **$3** (어제 실제 측정 10회차 = 약 $0.18). 넘으면 중단하고 그때까지 결과로 리포트
- 방식 비교 지표
  | 지표 | 의미 |
  |---|---|
  | **첫 질문까지 시간** | 회차 시작 → 첫 질문 응답 (②③은 늘어날 수 있음) |
  | **질문별 사용자 대기 시간** p50/p95/최대 (`answer_to_next_ms`) | 답을 보낸 뒤 다음 질문을 받기까지 |
  | **회차 전체 대기 시간** | 첫 질문까지 시간 + 질문별 대기 시간의 합 (사용자가 실제로 기다린 시간) |
  | 회차당 호출 수 (평균·최대) | 묶음·이중 요청 포함 |
  | 회차당 토큰·비용 | 버린 질문·버린 이중 요청 비용 포함 |
  | 미리 만든 질문 적중률·낭비율 | 방식 ①②③ |
  | 이중 요청 발생률, 두 번째 승리율, 추가 비용 | R4 |
  | 품질 지표 전부 | 첫 시도 통과율, 반복률, 계획 준수율, 위반율, 경고 표시율, 임신 질문 정확도, kind 일관성, 경로 일치율(6번 수정 방식) |
  | (③ 전용) 2단계 질문 품질 | 미리 만든 2단계 질문의 반복률, 이전 답과 맞지 않는 질문 비율(사람이 볼 수 있게 원문 목록 첨부) |
- **선택 기준** (리포트에 이 순서대로 판단 근거를 적는다)
  1. 품질 지표가 기준선보다 나빠진 방식은 탈락 ("반드시 0/100%" 항목은 하나라도 어긋나면 탈락)
  2. 남은 방식 중 **회차 전체 대기 시간 p95**가 가장 짧은 방식
  3. 차이가 작으면(10% 이내) **회차당 비용**이 낮은 방식
  4. 선택한 방식을 기본값으로 설정하고, R4 결과로 이중 요청 기본값(켬/끔, 대기 시간 N초)도 결정
- 결과: `results-v2.csv`에 실행별 행, 리포트 `backend/docs/perf/V2-latency-report.md` (방식별 비교 표, 선택 근거, 한계)
- 한계 명시: kind 기반 가상 사용자·페르소나 5명 기준이며 실제 사용자 분포를 대표하지 않음, 회차 수가 적어 p95가 흔들릴 수 있음

## 6. 측정 지표 수정: 경로 일치율
- 어제 실험 B의 `path_match_rate` 0.6은 실제 순서가 같았는데도 `CONCERN:<라벨>` 주제 이름에 선택지 문장이 들어가서 다르게 센 것
- `CONCERN:*` 주제는 라벨 대신 "몇 번째 파생 주제인지"(예: `CONCERN#1`)로 정규화해서 비교
- 기준선 값도 수정된 방식으로 다시 계산해 리포트에 함께 적기
- ⚠️ 이 지표는 kind 기반 가상 사용자·페르소나 1명 기준이라 서비스 전체의 일관성을 보장하지 않는다는 한계를 리포트에 명시

## 7. 정밀 추천 품질 개선 (확정)
**재현 화면 (2026-10-27 아침, 실제 API)**: 1번 회원(프로필: 신장 질환, 고혈압, 혈압약 이름 모름, 음주 많음, 흡연)으로 V2 진행 → 결과가
- 추천 성분 **0개** ("지금 추천할 성분이 없어요")
- 요약이 6문장짜리 **줄글**: "신장 질환의 단계와 혈압약 이름, 현재 영양제 복용 여부가 확인되지 않아 지금은 새 영양제 추천을 보류합니다. … 담당 의료진에게 음주량을 알리고 … 진료받고 …"
- 요약에는 "베타카로틴은 추천에서 제외했습니다"라고 쓰여 있지만 제외 성분 목록은 화면에 없음
어제 측정의 A3·A4 빈 목록과 같은 문제. **GPT가 안전 판단까지 스스로 해서 전부 보류한 것** → "성분은 GPT, 안전은 서버 규칙" 설계와 어긋남.

먼저 원인 확인: 위 회원의 최근 회차 `ai_recommendations.summary`, `ai_recommendation_items`, `llm_call_logs`(RECOMMEND 호출의 원본 응답)를 보고, GPT 원본이 정말 빈 목록이었는지, 규칙이 전부 제외한 것인지 구분해서 보고한다.

### 7-1. 신장 질환 규칙 추가
- 현재 `recommendation_rules` 39개에 질환 `KIDNEY` 조건 규칙이 **하나도 없음** → 서버가 막아주지 않으니 GPT가 전부 보류
- `domain-rules.md` 출처 방식대로, **공신력 있는 출처(NIH ODS, FDA 라벨, 식약처 등)를 확인한 규칙만** 추가. 출처를 확인하지 못한 성분은 넣지 말고 목록으로 보고
- 조치는 기본 `WARN`(추천하되 상담 안내). 출처에 "피해야 한다"가 명확한 경우만 `EXCLUDE`
- 시드 3곳(STEP07, 테스트 시드, STEP13 셋업) + `domain-rules.md` + 기존 DB용 STEP 시드 + `RuleEngineTest` + 골든 갱신
- 같은 방식으로 다른 질환(`THYROID`, `DIABETES`, `HYPERTENSION`)에도 규칙이 없는지 확인하고, 빠진 것은 목록으로만 보고 (이번에는 KIDNEY만 추가)

### 7-2. 추천 프롬프트 보완 (V1·V2 공통, 프롬프트 버전 올리기)
- "금기 성분·용량·상한은 서버가 별도로 검증하고 걸러낸다. 정보가 불확실하다는 이유로 추천을 비우지 말고, 도움이 될 수 있는 성분은 이유와 함께 고른다"
- "질환·복용 약 때문에 주의가 필요하면 성분을 빼지 말고 이유(reason)에 주의점을 적는다"
- 요약(summary): **2문장 이내, 100자 이내**. 진료·처방·검사 지시("진료받으세요", "의료진에게 알리세요", "검사 결과에 따라") 금지. 개별 성분 설명은 요약이 아니라 각 성분의 reason에
- V2 입력의 "현재 복용 중인 영양제: 모름"이 보류 근거로 쓰이는지 확인하고, 필요하면 "알 수 없음(이 경우 기준 권장량으로 계산됨)"처럼 서버 동작을 같이 알려주는 문구로 변경

### 7-3. 서버 검증 추가
- 요약 길이 초과 → 서버가 자르지 말고 검증 실패로 1회 재요청 (기존 재요청 구조 재사용)
- 요약에 금지 표현(V2 질문 검증기의 금지어 + "진료", "처방", "의료진", "검사 결과") → 1회 재요청. 그래도 실패하면 요약을 서버 고정 문구로 대체 ("입력하신 정보를 바탕으로 고른 성분이에요.")
- 추천 성분이 0개인 응답 → 1회 재요청 (사유: "성분을 1개 이상 고를 것, 안전은 서버가 검증"). 그래도 0개면 저장은 하되 아래 7-4로 표시

### 7-4. 빈 결과 화면 처리
- 최종 추천이 0개일 때 GPT 요약 대신 고정 안내: "입력하신 건강 정보로는 지금 바로 권할 성분이 없어요. 복용 중인 약이나 질환이 있다면 의사·약사와 상담해 주세요."
- 제외 성분(`excludedItems`)이 있으면 "안전을 위해 제외한 성분" 목록은 항상 보이게 (지금 화면에서 안 보이는 이유도 확인: GPT가 아예 안 고른 것인지, 화면 조건 문제인지)

### 7-5. kind 판단 보완 (V2 질문 프롬프트)
- "없어요"(= 수량 0)가 NONE으로 붙는 문제: kind 정의에 "NONE은 그 상황 자체가 해당되지 않을 때만. 양이 0인 선택지는 의미로 판단(예: 햇빛 0분 → CONCERN)" 추가

### 7-6. 확인
- 위 1번 회원 프로필로 V2를 다시 실제 API로 2~3회 돌려서 추천이 1개 이상, 요약 2문장 이내, 금지 표현 없음, 신장 규칙 경고 표시를 확인 (스크린샷이 어려우면 API 응답 원문)
- V1·V2 기존 테스트·골든 통과, 프롬프트 버전 변경에 따른 골든 갱신은 이유와 함께 커밋
- 이 변경은 5번 속도 측정과 **분리**해서 측정 (R0 기준선을 7번 적용 후에 다시 잡으면 품질·속도 효과가 섞이지 않음)

## 8. (선택) 기본 파이프라인 버전 — 계획 단계에서 확인받기
- `RecommendationProperties.pipelineVersion` 기본값이 `V0`(규칙 없음). `local-llm` 프로필 등에서 V4로 쓰고 있지만, 설정이 없는 환경에서는 V1 추천 API가 규칙 없이 동작할 수 있음
- 기본값을 `V4`로 바꾸는 안과 영향(골든 테스트, 평가 기본값 등)을 정리해서 제안

## 9. (선택) OSIV 끄기 검토 — 계획 단계에서 확인받기
- 문제: `spring.jpa.open-in-view`를 설정하지 않아 Spring Boot 기본값(켜짐). 요청 중 처음 DB를 쓴 뒤 **응답이 끝날 때까지 커넥션을 붙잡을 수 있음** → 추천·V2 질문 API는 GPT 대기(10~60초) 동안에도 커넥션을 쥐고 있을 수 있음. HikariCP 기본 10개라 동시 추천 요청이 10개를 넘으면 다른 API까지 DB 대기. LLM 호출을 트랜잭션 밖으로 분리한 설계와 Bulkhead(20)가 무력화됨 (`backend/docs/progress.md`에도 "OSIV 영향 확인 — 미룸"으로 남아 있음)
- 할 일
  1. 먼저 **현재 상태를 측정**: 로컬 서버(Fake LLM에 지연을 줘서 GPT 대기를 흉내)에서 추천 요청을 동시에 여러 개 보내고, Hikari 활성 커넥션 수(`hikaricp.connections.active` 메트릭)와 다른 API(예: 홈) 응답 시간을 기록
  2. `spring.jpa.open-in-view=false`로 바꾸고 **전체 테스트 실행** → `LazyInitializationException`이 나는 곳 목록 작성 (트랜잭션 밖에서 지연 로딩, 엔티티를 그대로 응답으로 반환하는 컨트롤러 등)
  3. **AI 담당 코드에서 나는 것만** 고친다 (트랜잭션 안에서 DTO 변환 또는 fetch join). 다른 팀원 코드에서 나는 것은 고치지 말고 파일·메서드·원인을 목록으로 보고
  4. 1번과 같은 조건으로 다시 측정해서 커넥션 점유가 줄었는지 Before → After로 기록
- 설정 파일이 팀 공통이므로, 다른 팀원 코드에서 예외가 하나라도 나면 **설정은 바꾸지 말고 보고만** 하고 멈춘다 (팀 협의 후 적용)
