## 목표

지금 마이페이지 [추천 제품 보기]는 **가장 최근 추천 1건**만 보여준다. 이것을 **최근 추천 기록 20건**으로 바꾼다. 기록 하나 = 추천 한 번 (V1 설문 / V2 맞춤 질문 / V4 대화창, 시간순으로 섞음). 기록마다:

1. **언제** 추천받았는지 (완료 시각)
2. **어디가 불편했는지** — 맨 처음 받은 "불편한 점" 답 (**90일까지만**, 개인정보)
   - V1 설문: `Q-GOAL` ("뭐가 불편하세요? …", MULTI)에서 고른 선택지 라벨
   - V2 맞춤 질문: 첫 LLM 질문 `CONCERN_OPEN`에서 고른 선택지 라벨
   - V4 대화창: 처음 입력한 문장 (+ 되묻기 답)
3. **그때 추천받은 성분과 제품** — 성분 순서 + 성분별 **제품 순위 그대로**

## 설계 원칙

1. **추천 결과는 남기고, 불편한 점(원문)은 90일 뒤 지운다.**
   - 추천 결과 = 언제·어떤 성분·어떤 제품(순위). 회원(`user_id`) 기준으로 남는다.
   - 불편한 점 = 설문 답·맞춤 질문 답·대화 원문. 90일 뒤 삭제 (V2·V4는 지금처럼 세션과 함께, **V1 Q-GOAL은 이번에 추가**).
2. **기록은 "추천받던 그때의 결과"를 보여준다.** 그래서 제품 순위를 추천이 끝날 때 저장한다.

### 데이터 구조 (이번 작업 후)

### "잠이 안와요" 예시 — 바뀐 뒤 저장 흐름
- 대화 시작 → `ai_chat_sessions` 1행 (그대로)
- 입력 → `ai_chat_turns`에 원문 (그대로, 90일 보관)
- 트랙 1 결과 → `ai_chat_results` (`track = REVIEW`, `cards`) **+ `user_id`**
- 트랙 2 결과 → `ai_recommendations`(PENDING → DONE) **+ `user_id`**, DONE 순간 **성분별 제품 순위 → `ai_recommendation_products`**
- 90일 뒤 → 세션·원문 삭제. 트랙 1 결과 행은 **남고** `chat_session_id`만 NULL, 트랙 2 추천도 `user_id`로 남음 → 기록에 "대화창 추천 · 마그네슘(제품 3개)"은 남고 불편한 점만 "90일이 지나 삭제됐어요"

## 절대 조건

1. **LLM·임베딩 호출 0회** — 기록 API와 제품 저장 모두 저장된 데이터·기존 V3 계산만 쓴다.
2. **본인 것만** — 남의 기록 id로 상세를 부르면 존재를 숨기는 404, 비회원 401.
3. **추천이 제품 저장 때문에 실패하면 안 된다** — 저장이 실패해도 추천은 DONE 그대로, 경고 로그 + 메트릭만.
4. **안전 판단 유지** — 저장할 제품은 `ReviewProductRecommendationService.recommend(recId, ingredient)` 결과(조건 로더·`ProductSafetyFilter` 통과)만. 필터를 우회하는 쿼리를 만들지 않는다.
5. **기존 동작 유지** — V1·V2·V4·V3 흐름과 API 응답, 기존 테스트. DB에 더 쓰이는 행·컬럼(`user_id`, 제품 순위)은 의도된 변경이며, 테스트·골든이 DB 행을 비교한다면 **그 부분만** 기대값을 고치고 이유를 보고서에 적는다.
6. **원문 보관 기간 유지** — `ai_chat_turns`(원문)·`ai_question_turns`는 지금처럼 세션과 함께 90일 뒤 삭제돼야 한다. 결과 행에 원문을 옮겨 담지 않는다.
7. **다른 팀원 도메인 수정 금지** — `users`, `health`, `intake`, `notification`, `product`(catalog) 등. `users`·`catalog_products`는 FK로 참조만 하고 구조를 바꾸지 않는다. `domain/survey`는 영준 담당(git 이력 확인)이라 **Q-GOAL 삭제 쿼리·메서드 추가만** 허용.

### 3-2. 확인할 것 (파일:줄 근거)
1. **DONE 경로 전부**가 `RecommendationStore.complete`를 지나는지: V1 회원·비회원(동기·큐), V2, V4 트랙 2, RULE_ONLY 폴백. 안 지나는 경로가 있으면 목록으로.
2. **제품 저장 시점·트랜잭션**: `recommend()`는 DB에서 추천·조건을 다시 읽으므로 DONE 커밋 **이후**에 호출해야 하는지(`@TransactionalEventListener(AFTER_COMMIT)` 등). 동기/비동기, 추천 응답 지연 영향(V7 측정: 성분 1개 10쿼리·3개 20쿼리). 기본안: **커밋 후 같은 스레드, 실패 격리** — 지연이 크면 비동기안과 비교해 제안. V4 트랙 2는 이미 백그라운드 실행기라 지연 영향이 없는지.
3. **`user_id` 넣는 곳**: 새 추천 생성 시 경로별 회원 id(V1 `response.user`, V2 `session.user`, V4 `chatSession.user`), 트랙 1 결과 저장 시(`saveReviewResult` — 일반·재사용 복사 둘 다), 트랙 2 `startFallback`의 `ai_chat_results` 행.
4. **`ai_chat_results` 세션 NULL 허용의 영향**: `AiChatResult.chatSession`을 optional로 바꿀 때 영향받는 코드 전부 — `ChatSessionStore.result(chatSessionId)`·`findReusable`(세션 없는 결과가 재사용되지 않는지), `ChatRecommendationService.get`·`snapshot`, V7 `RecentRecommendationService`(NPE), 대화 API 응답. UNIQUE(`chat_session_id`)는 NULL 여러 개 허용(MySQL)인지 확인.
5. **90일 정리 순서**: 세션 삭제 시 `ai_chat_turns`는 CASCADE로 지워지고 `ai_chat_results`는 SET NULL로 남는지. JPA `@OnDelete` 변경과 DB FK가 같은 동작인지 (`deleteStartedBefore`가 벌크 삭제인지 엔티티 삭제인지).
6. **제품 테이블 설계** (초안 4-1)와 FK. 제품 0개 성분은 행 없음.
7. **저장된 id로 제품 표시**: `ReviewProductResponse.Product`(이름·브랜드·사진·참고 가격·메달 등, #119/#122 이후 형식)를 id로 만드는 기존 방법. 판매 중단·차단 제품 제외(D12) 방법.
8. **V1 Q-GOAL 90일 삭제**: 기준(`survey_responses.submitted_at` < now − 90일), 대상(회원·비회원 모두), 지운 뒤 Q-GOAL을 다시 읽는 코드가 없는지(`RecommendationInputAssembler`는 생성 시점에만? V3 `RecommendationConditionLoader`가 goals를 쓰는지? V2 모니터링·`/latest`?). **응답(`survey_responses`)·다른 답은 지우지 않는다.**
9. V1 Q-GOAL 라벨을 얻는 방법 (`SurveyResponseDetail`에 라벨이 있는지, 없으면 survey 도메인 읽기 메서드 추가).
10. V2 `CONCERN_OPEN` 턴(회차당 1개, 답 없이 끝난 경우), V4 첫 턴·되묻기 답, V5 재사용 시 같은 내용 2건(기본안: 중복 제거 안 함).
11. 목록 조립 쿼리 수 (20건 기준, 출처별 일괄 조회).
12. 기존 테스트·골든 중 `ai_recommendations`·`ai_chat_results` 행·컬럼을 비교하는 것 목록.
13. 엔티티 ↔ DDL 대조 방법 (V4 때처럼 `ddl-auto=create` 결과와 information_schema 비교).

### 4-1. DB 변경 (초안)

```sql
-- ① ai_recommendations: 회원 연결 (V1·V2·V4 트랙 2)
ALTER TABLE ai_recommendations ADD COLUMN user_id BIGINT NULL COMMENT '회원 추천의 회원 (비회원 NULL)';
ALTER TABLE ai_recommendations ADD KEY idx_ai_recommendations_user (user_id, finished_at);
ALTER TABLE ai_recommendations ADD CONSTRAINT fk_ai_recommendations_user
  FOREIGN KEY (user_id) REFERENCES users (user_id) ON DELETE SET NULL;   -- D15: 탈퇴 처리는 후속 결정

UPDATE ai_recommendations r JOIN survey_responses s ON r.response_id = s.response_id
   SET r.user_id = s.user_id WHERE r.user_id IS NULL AND s.user_id IS NOT NULL;

  catalog_product_id        BIGINT NOT NULL,

  created_at                DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uq_ai_rec_product_rank (recommendation_item_id, product_rank),
  CONSTRAINT fk_ai_rec_products_item FOREIGN KEY (recommendation_item_id)
    REFERENCES ai_recommendation_items (recommendation_item_id) ON DELETE CASCADE,
  CONSTRAINT fk_ai_rec_products_product FOREIGN KEY (catalog_product_id)

-- ③ ai_chat_results: 회원 연결 + 세션이 지워져도 결과 보존 (V4 트랙 1)

ALTER TABLE ai_chat_results ADD CONSTRAINT fk_chat_results_user
  FOREIGN KEY (user_id) REFERENCES users (user_id) ON DELETE SET NULL;  -- D15
ALTER TABLE ai_chat_results DROP FOREIGN KEY fk_chat_results_session;
ALTER TABLE ai_chat_results MODIFY chat_session_id BIGINT NULL;
ALTER TABLE ai_chat_results ADD CONSTRAINT fk_chat_results_session
```
